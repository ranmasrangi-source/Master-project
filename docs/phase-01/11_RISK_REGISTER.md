# DOC-P01-11 — Master Risk & Security Remediation Register

## 1. Ten Critical Security Findings Tracking Register (`SEC-DB-001` through `SEC-PRIV-001`)

| Finding ID | Severity | Title | Root Cause in Initial Prototype | Remediation Implemented in Stage B | Verification Test Suite | Status |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **`SEC-DB-001`** | `CRITICAL` | Persistent Database & Audit Storage | All state lived in React `useState` memory; fake `wormReplicated: true` boolean. | Implemented persistent SQLite database (`/src/server/db.ts`) using `node:sqlite` (`DatabaseSync`) with WAL mode, foreign keys, ACID transactions, SQL `BEFORE UPDATE/DELETE` immutability triggers on `audit_events`, and honest `wormReplicated: false` (`LOCAL_SQLITE_TRIGGER_IMMUTABLE`). | `src/tests/foundation.test.ts` (Database persistence, FK constraints, concurrent writes & SQL trigger immutability tests) | `FIXED AND TESTED` |

| **`SEC-RBAC-001`** | `CRITICAL` | Strict 1,680-Permutation Server RBAC | Permissive `READ` fallback granted `SPONSOR_ACCOUNT` access to private submissions/decisions; blocked `CREATE` submission. | Removed permissive fallback; implemented explicit deny-by-default rules for all `15 roles × 14 resources × 8 verbs = 1,680` permutations in `/src/data/governanceAndPhases.ts` and enforced server-side RBAC middleware on every protected API route. | `src/tests/rbac1680.test.ts` (Exhaustive 1,680-permutation policy verification test + API authorization tests) | `FIXED AND TESTED` |
| **`SEC-GOV-001`** | `CRITICAL` | Backend Governance & Authority Enforcement | Stage transitions and governance actions ran only in browser state. | Implemented backend governance endpoints enforcing Researcher scope (Stages 1–3) vs. Dual-Control (`2P`) Governance authority (Stages 4–5), commercial firewall isolation, and mandatory audit logging. | `src/tests/foundation.test.ts` (Backend stage transition authorization & sponsor/commercial firewall tests) | `FIXED AND TESTED` |
| **`SEC-GOV-002`** | `CRITICAL` | Server-Side Human Verification & Appeal Workflows | Verification and appeal decisions executed only in client `useState`. | Implemented transactional backend endpoints (`POST /api/v1/submissions/:id/review`, `POST /api/v1/submissions/:id/appeal`, `POST /api/v1/submissions/:id/appeal-decision`) enforcing 5-Signal COI, COI attestation, Tier-A Dual Review, split-vote escalation (`ESCALATED_SPLIT_DECISION`), `REQUEST_ADDITIONAL_EVIDENCE`, and free certificate issuance only upon human approval. | `src/tests/foundation.test.ts` (End-to-end server verification, 5-Signal COI block, split-vote escalation, and independent appeal tests) | `FIXED AND TESTED` |
| **`SEC-GOV-003`** | `CRITICAL` | Genuine Two-Person (`2P`) Dual-Control | Single click by one actor published destinations or revoked certificates. | Implemented persistent `dual_control_Approvals` table and state machine requiring two distinct authenticated principals (`initiator_user_id !== cosigner_user_id`) for Stage 4/5 destination publication and certificate revocation, with expiration and cancellation rules. | `src/tests/foundation.test.ts` (Dual-Control `2P` test proving single principal cannot self-cosign destination publication or certificate revocation) | `FIXED AND TESTED` |
| **`SEC-EVID-001`** | `CRITICAL` | Real Evidence Ingestion, Validation & Parsing | Self-reported numeric inputs instead of real file uploads and parsing. | Implemented `POST /api/v1/evidence/upload` supporting real binary/multipart file ingestion, magic-byte & size validation, XXE-blocking XML/PDF inspection, GPX trackpoint parsing (Haversine apex distance, max elevation, 15m rolling ascent rate, 2 km residential masking), JPEG EXIF header extraction, SHA-256 hashing, duplicate hash detection, and signed short-TTL vault download tokens (`/src/server/evidenceProcessor.ts`). | `src/tests/foundation.test.ts` (Real GPX/JPEG/PDF upload, XXE payload rejection, duplicate SHA-256 detection, and private vault token authorization tests) | `FIXED AND TESTED` |
| **`SEC-PRIV-001`** | `CRITICAL` | Privacy Vault, Key-Shredding & Coordinate Masking | Raw PII in submissions/audit logs; incomplete GDPR erasure simulation. | Implemented `user_pii_vault` encrypted with AES-256-GCM per-user `user_dek` keys, opaque `internal_actor_uuid` references in audit logs, 2 km residential GPX masking, post-issuance holder privacy preference updates, and transactional `user_dek` key-shredding + submission/certificate PII redaction (`/src/server/privacyVault.ts`). | `src/tests/foundation.test.ts` (AES-256-GCM PII encryption, residential coordinate masking, post-issuance privacy toggle, and key-shredding erasure verification) | `FIXED AND TESTED` |
